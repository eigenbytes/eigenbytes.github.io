Hands-On: Azure Data Lake to Feature Store

A guided, beginner-friendly walkthrough that explains not only the how but also the why behind each step.

Big Picture: Modern ML workflows need consistent features across training and serving. This tutorial shows how to take raw data in Azure Data Lake, clean it with Spark, and register it into a feature store (e.g. Feast). By the end, you’ll understand both the technical steps and the reasoning behind them.

Step 1 — Why Azure Data Lake + Feature Store?

Azure Data Lake Storage Gen2 is a cost-effective way to store raw data (CSV, Parquet, JSON). It’s optimized for analytics workloads and can scale to petabytes.

Feature Stores act as the “single source of truth” for ML features. They ensure that the features you train on are the exact same features you serve to your model in production.

Why this matters: Without a feature store, it’s common to have “training/serving skew,” where features are computed differently in offline vs online systems, causing models to underperform.

Step 2 — Prerequisites

  • An Azure subscription with Data Lake Storage set up
  • A Databricks (or Spark) workspace to run transformations
  • A running Feature Store (Feast, Databricks FS, or Tecton)
  • Some sample data (e.g., a transactions.csv file uploaded to a container called raw-data)
Tip: Keep raw data immutable. Always create transformed “feature tables” separately, so you never overwrite your raw ground truth.

Step 3 — Connect to Azure Data Lake

We use OAuth-based authentication to mount the data lake into Spark. Replace placeholders with your own IDs/secrets.


spark.conf.set("fs.azure.account.auth.type.<account>.dfs.core.windows.net", "OAuth")
spark.conf.set("fs.azure.account.oauth.provider.type.<account>.dfs.core.windows.net",
  "org.apache.hadoop.fs.azurebfs.oauth2.ClientCredsTokenProvider")
spark.conf.set("fs.azure.account.oauth2.client.id.<account>.dfs.core.windows.net", "<CLIENT_ID>")
spark.conf.set("fs.azure.account.oauth2.client.secret.<account>.dfs.core.windows.net", "<CLIENT_SECRET>")
spark.conf.set("fs.azure.account.oauth2.client.endpoint.<account>.dfs.core.windows.net", 
  "https://login.microsoftonline.com/<TENANT_ID>/oauth2/token")

df = spark.read.csv("abfss://raw-data@<account>.dfs.core.windows.net/transactions.csv", header=True, inferSchema=True)
df.show(5)

Explanation: Here we’re instructing Spark how to authenticate to Azure’s secure storage layer. Once mounted, reading a CSV feels no different than reading a local file — but under the hood, it’s coming from cloud storage.

Step 4 — Clean & Transform Data

Real-world raw data is rarely ready for modeling. You usually need to:

  • Handle missing values
  • Create derived features (ratios, flags, buckets)
  • Normalize timestamps

from pyspark.sql.functions import col, when, dayofweek

# Example: create new features
features_df = df.withColumn("is_high_value", when(col("amount") > 100, 1).otherwise(0)) \
                .withColumn("day_of_week", dayofweek(col("timestamp")))

features_df.printSchema()

Explanation: We’ve derived two new features: a binary “high value” flag, and the day of week. These features are simple, but illustrate how business logic is encoded for ML.

Step 5 — Register Features in a Feature Store

With Feast (an open-source feature store), you define entities and feature views. Entities represent the thing you’re predicting on (e.g., customer_id), while feature views describe the features tied to those entities.


from feast import Feature, Entity, FeatureView, Field
from feast.types import Int64, String, Bool

# Define entity
customer = Entity(name="customer_id", join_keys=["customer_id"])

# Define feature view
transaction_fv = FeatureView(
    name="transaction_features",
    entities=[customer],
    ttl=None,
    schema=[
        Field(name="is_high_value", dtype=Bool),
        Field(name="day_of_week", dtype=String),
    ],
    online=True,
)

# Apply to store
store.apply([customer, transaction_fv])

Explanation: Once applied, the feature store now “knows” how to compute and serve these features consistently, whether you’re training offline or serving online.

Step 6 — Validate Your Features

Always verify that your features are accessible and correct before plugging them into models.


store.get_historical_features(
    entity_df="SELECT customer_id, event_timestamp FROM transactions",
    features=["transaction_features:is_high_value", "transaction_features:day_of_week"],
).to_df().head()

Explanation: This checks that historical feature retrieval works — a critical step for reproducibility in training pipelines.

Takeaways

  • Consistency: The same features feed training and production.
  • Scalability: Azure Data Lake holds vast raw datasets cheaply.
  • Modularity: Spark transforms → Feature definitions → Reusable assets for multiple models.
